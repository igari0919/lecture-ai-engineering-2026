- 検索だけを実行して見つかったページと、その本文で確認できたこと：
  - `search_materials`（および `app.retrieval`）のベクトル検索により、`lec02-main`（基盤モデルの仕組み）の **p.52「LoRA と QLoRA ：大きなモデルも GPU 1 台で調整できる」** などが上位にヒットした。
  - 本文から、LoRA は「元の重みを固定し、変化分を表す小さな追加部分（行列A・B）だけを学習すること」、QLoRA は「それに加えて元の重みを 4bit に圧縮すること」が明記されているのを確認できた。

- `--trace`で見えたツール呼び出し（ツール名・引数・回数、Treeでたどった目次など）：
  - **全文投入（`--full-context`）**：ツール呼び出し **0回**（`tools=[]` で全資料 227,971文字を一括投入／モデル応答 1回）。
  - **ベクトル検索**：`search_materials({'query': 'LoRA 固定 学習 QLoRA 追加'})` を **1回** 呼び出し（モデル応答 2回）。
  - **Tree（`--tree`）**：`browse_tree` を **計4回** 呼び出し（モデル応答 5回）。たどった階層は以下の通り。

- 取得した情報が足りなかった例、取得できたのに回答へ使えなかった例：
  - **取得した情報が足りなかった例**：
    - 今回の質問自体はp.52に核心が書かれていたため4方式とも回答に必要な情報は取得できたが、ベクトル検索では単一ページのヒットが中心となるため、複数ページにまたがる説明（p.51のPEFTの全体像やメモリ削減の背景など）の補足文脈は欠けやすい状態だった。
  - **取得できたのに回答へ使えなかった例**：
    - **全文投入**：`lec02-main` の p.51・p.52 の正しい本文を取得できていたにもかかわらず、同時投入された演習資料（`lec02-exercise` 等）の「宿題のルール」に引っ張られ、直接の答えを出さずヒントのみを返す結果となった。
    - **ベクトル検索・Graph**：上位候補やグラフ拡張で複数ページを取得する仕組み上、質問の直接の根拠（p.51・p.52）以外の候補ページは回答生成には使われず、コンテキスト（入力トークン）として消費される。

- 今回の用途に採用したい方式と、その理由・比較条件の限界：
  - **採用したい方式**：**Graph（`--graph`）**（次点で **ベクトル検索**）。
  - **理由**：
    - 全文投入は 1回約11.7万トークン（$0.035795）と高コストで、無料枠の 1分間あたり入力トークン上限（250,000 tokens/分）にすぐ達するうえ、無関係な資料の混入で回答方針がブレる。
    - Tree はピンポイントで高精度だが、モデル応答 5回・18.85秒と待ち時間が長く対話テンポを損なう。
    - Graph は応答 2回・3.35秒・$0.002194（全文投入の約 1/16 の費用）と高速・低コストでありながら、1ページに収まらない前後の文脈（p.51 と p.52）を自然に補完でき、共通用語（`mentions`）による関連スライドの横断にも対応できるため。
  - **比較条件の限界**：
    - 今回は **1問のみ・各1回の実行** による比較であり、複数講義をまたぐ比較質問や抽象度の高い質問での再現性・ばらつきまでは検証できていない。
    - 全文投入のみ `RAG_DOCUMENT_IDS` のフィルタがかからず全9資料（演習・案内含む）が入力されており、他の 3方式（第1〜3回本講義の 3資料のみ）と検索対象の範囲が同一条件ではない。
    - 埋め込み生成やインデックス構築にかかる時間・コストは計測対象外となっている。

- 気づき・疑問：
  - **資料範囲の違いが回答の振る舞いまで変える**：全文投入は全資料を一括投入するため、講義資料だけでなく演習資料の「宿題ルール」までコンテキストに入り、「答えを直接言わない」という意図しない制約が強く働いた。コンテキストは多ければ良いわけではなく、対象範囲の設計が重要だと思った。
  - **Tree と Graph の役割分担の違い**：どちらも事前に作成した JSON（`tree.json` / `graph.json`）を Python で辞書引きする仕組みだが、Tree は「AIが目次を読んで次を判断する（目次情報など都度都度の判断にはAIによる解釈が含まれるためGraphと比べると低速）」、Graph は「スクリプト側が一括で隣接・共通用語ノードを広げる（AIによる判断は必要なく、単語の繋がりを追うだけでいいので高速）」という設計思想の違いが明確になった。どちらのJSONファイルも作成時に、目次が適切な形で書かれていたり、Graph情報も単語間の繋がりについての記述に誤りがないことが前提になる。つまり、事前の資料作りが重要だと思った。
  - **疑問**：複数の講義回をまたいで比較するような質問や、スライドタイトルにキーワードが含まれない抽象的な質問を投げた場合、ベクトル検索・Tree・Graph の精度や応答回数の差はどのように変化するか確認する必要があると思った。
